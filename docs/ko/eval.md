# 검색·그룹 평가

의미 검색과 주제 그룹을 점수로 재는 eval 두 가지. `db.py`, `grouping.py`, `eval/`을 바꿨을 때 결과가 좋아졌는지 나빠졌는지 확인하는 용도.

## 정답 보관 위치
정답은 별도 Neon branch(`EVAL_DATABASE_URL`)에 보관. 정답을 만들 때의 보관함 사본도 같은 branch에 있고, 두 eval 모두 여기서 실행.

- 새 대화가 쌓여도 점수 변화 없음
- 정답에 개인 대화가 인용되어 있어 공개 저장소에 올리지 않음
- 두 eval 모두 LLM 호출 없음. 질문은 임베딩과 함께 저장되어 있어 실행 비용 0, 같은 코드면 항상 같은 점수

실행할 때마다 결과를 그 branch의 `eval_reports`에 저장. `--accept`로 받아들인 실행이 기준선이고, 이후 실행은 기준선과 비교.

## 실행
```bash
uv run --group eval --env-file .env python eval/run.py                      # 점수 계산, 기준선과 비교
uv run --group eval --env-file .env python eval/run.py --accept             # 이번 실행을 기준선으로
uv run --group eval --env-file .env python eval/run.py --set T_SMALL=0.30   # 그룹 상수를 바꾸기 전에 시험
git config core.hooksPath .githooks                                         # 검색 코드 push 전 자동 실행
```

pre-push hook은 `db.py`, `grouping.py`, `eval/`이 바뀌었을 때만 eval 실행. 점수가 떨어지거나 eval이 실패하면 push 중단. `git push --no-verify`로 한 번 건너뛰기 가능.

## meaning: 맞는 대화, 맞는 위치
검토를 마친 질문 62개. 질문마다 답이 되는 대화, 대부분은 답이 있는 메시지까지 기록.

| 유형 | 질문 수 | 정답 |
|---|---|---|
| paraphrase | 20 | 다른 표현으로 물은 대화 |
| pinpoint | 20 | 답이 들어 있는 메시지 하나 |
| context | 12 | 대화 전체 |
| absent | 10 | 없음. 보관함에 없는 주제 |

| 점수 | 통과 조건 |
|---|---|
| rank1, rank3, rank5 | 정답 대화가 상위 1, 3, 5개 결과 안에 포함. absent 질문은 그 결과들의 평균 유사도가 0.35 미만이면 통과 |
| section | 결과의 구간이 정답 메시지를 포함(paraphrase, pinpoint만) |

기준선에서 통과하던 질문이 지금 실패하면 퇴보로 판정.

## groups: 맞는 대화끼리 묶기
같은 보관함을 LLM으로 두 번 따로 분류해 그룹 두 벌 생성. 두 번 모두 같이 묶은 대화 쌍, 두 번 모두 따로 둔 대화 쌍이 정답. 두 분류가 엇갈린 쌍은 채점 제외. eval은 Refresh groups와 똑같은 방식으로 작은 그룹을 다시 만들고 그 쌍으로 채점.

| 점수 | 의미 |
|---|---|
| precision | 같이 묶은 쌍 가운데 실제로 같은 그룹이어야 하는 쌍의 비율 |
| recall | 같은 그룹이어야 하는 쌍 가운데 실제로 같이 묶은 쌍의 비율 |
| F1 | 둘을 합친 점수. 떨어지면 퇴보로 판정 |

## 측정으로 정한 것
아래는 2026년 7월 검색과 그룹을 만들면서 잰 결과. 지금의 질문 세트가 생기기 전 측정. 이렇게 정한 값은 [구조 문서의 측정값 표](ARCHITECTURE.md#측정값과-근거)에 정리.

### 평균이 아닌 조각 단위로 검색
정답이 정해진 질문 66개에서 첫 결과가 맞은 비율:

| 검색 단위 | 첫 결과 정답률 |
|---|---|
| 대화마다 평균 벡터 하나 | 48% |
| 메시지 하나씩 | 59% |
| 1,500자 조각 | 68% (나중에 실제 데이터로 다시 재서 70%) |

평균은 대화 전체가 무엇에 관한 것인지를 표현. 그룹 묶기에는 필요하지만 검색에는 너무 흐릿하고, 대화 하나가 모든 주제의 한가운데에 놓여 상관없는 질문에도 1등으로 나오는 문제 발생. 메시지 하나는 주변 맥락이 부족한 경우가 많음. 조각은 그 중간이고, 벡터 저장 공간도 메시지 단위의 약 65 MB 대신 24 MB.

### 길이로 가중한 평균
그룹 묶기에는 여전히 대화마다 벡터 하나 사용: 조각들의 평균. 메시지마다 같은 비중으로 평균을 내자 짧은 메타 발언이 글자 수로는 37%인데 표는 53%를 차지해, 대화 하나가 엉뚱한 그룹에 배치. 지금은 조각마다 자기 길이만큼 반영.

### "비슷한가?"는 기하, "무슨 종류인가?"는 LLM
벡터 거리는 같은 주제의 대화를 잘 찾음. 그래서 작은 그룹은 기하로 묶기. 큰 분류에는 지식이 필요: 객체 인식과 멀티 에이전트는 둘 다 AI지만 벡터는 서로 멀리 위치. 큰 분류를 기하만으로 묶었을 때 거의 혼자인 그룹 7개 발생.

지금은 LLM이 두 번의 호출로 이름 짓기: 먼저 각 분류가 담을 내용과 함께 분류를 만들고, 다음에 작은 그룹을 하나씩 분류에 배치. 한 번의 호출로 둘 다 시켰을 때는 소프트웨어 프로젝트를 구직 분류에 넣는 실수 발생. 그룹 36개 기준 두 번 호출 방식의 잘못 배치 수는 `gpt-4.1-mini` 약 6개, `gpt-5.4-mini` 5개, `gpt-5.5` 3개, 재분류 한 번 비용은 각각 $0.01, $0.02, $0.18. sgmcp는 `gpt-5.4-mini` 사용.
